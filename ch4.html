Chapter 4

Comments

Comments are the parts of your code the compiler never sees. They are how you communicate with the next person who reads your program — including future you.

4 Topics // · /* */ · commenting out · best practice
Topic 1

Single-Line Comments — //

✅ Complete

Compile and run this — count how many lines of text actually appear in the output.

A single-line comment starts with // and ends at the end of that line. Everything after // on that line is completely ignored by the compiler.

Comments exist for humans — to explain what the code does, why a decision was made, or to leave a note. They have zero effect on output, speed, or compiled size.

You can put a comment on its own line, or after code on the same line. Both are valid.

Single-Line Comment
// This entire line is a comment int age = 20; // comment after code — also valid // The compiler never sees anything after // printf("Hello\n"); // this line still runs
⚠
Common Mistake — Commenting the wrong part
printf("Hi"); // printf("Bye"); — only the second printf is commented. The first still runs. The // does not go backward — it only affects everything after it on that line.
🌍 Comments in production code

Real codebases comment why, not what — the code already shows what. Good comments explain decisions that are not obvious from reading the code.

// Use int, not char, to safely hold EOF (-1)
int c = getchar();

// Linux kernel: this loop avoids a race condition during boot
while (!cpu_ready()) { cpu_relax(); }

Topic 2

Multi-Line Comments — /* */

✅ Complete

Run this — the program has 10 lines in main but only two printf calls. What prints?

A multi-line comment opens with /* and closes with */. Everything between those two markers is ignored by the compiler — including newlines, blank lines, and code.

Multi-line comments cannot be nested. If you write /* outer /* inner */ end */, the compiler sees the first */ and closes the comment — the text after it is not a comment and will likely cause an error.

Multi-Line Comment
/* This is a single-line use of block comment syntax */ /* * Multi-line block comment. * The * at the start of each line is just a style convention. * The compiler only cares about the opening slash-star * and the closing star-slash. */ /* First comment */ /* Second comment */ // two on one line: valid
⚠
Critical Mistake — Forgetting the closing */
If you open /* and never close it, the compiler treats everything after it — including your actual code — as a comment. Your program will fail to compile. Always pair /* with */.
🌍 Block comments for function documentation

In real C code, multi-line comments document function behavior, parameters, and return values — especially in header files and library APIs.

/*
 * calculate_bmi - Computes Body Mass Index
 * @weight_kg: weight in kilograms
 * @height_m:  height in meters
 * Returns: BMI as a double (weight / height^2)
 */
double calculate_bmi(double weight_kg, double height_m);

Topic 3

Comments in Practice — When and How

✅ Complete

Run this well-commented program. Then read the comments — notice what each one explains and why.

Good comments explain why — not what. The code already shows what it does. Comments answer questions the code cannot: why this approach, why this value, why this order.

Bad comment: i++; // increment i — redundant, adds no information. Good comment: i += 2; // step by 2 to skip even indices — explains the non-obvious choice.

Comment quantity rule: too few comments leaves the next reader confused. Too many comments makes the code hard to read. Comment at decision points, not every line.

Where Comments Add Value
/* 1. BEFORE FUNCTIONS — explain purpose, parameters, return */ /* 2. BEFORE COMPLEX LOGIC — explain the algorithm */ /* 3. ON CONSTANTS — explain what the magic number means */ /* 4. ON WORKAROUNDS — explain why a normal approach failed */ #define MAX_RETRY 3 // retry limit before giving up #define TAX_RATE 0.12 // 12% sales tax (updated 2024) // Use abs() to handle negative temperatures correctly float temp_diff = abs(temp_a - temp_b);
🌍 Comments in the Linux kernel

The Linux kernel has millions of lines of C code. It uses a strict comment style — block comments document every exported function, single-line comments explain non-obvious decisions inline.

/*
 * This is a common optimisation trick: the compiler can
 * generate better code if it knows when a branch is unlikely.
 */
if (unlikely(error)) {
    handle_error();
}

Topic 4

Commenting Out Code — Temporarily Disabling Lines

✅ Complete

Run this program. It prints three lines. Now comment out line 5 (the second printf) and run again — what changes?

Commenting out code means putting // or /* */ around lines you want to temporarily disable without deleting them. The compiler skips them; you can restore them by removing the comment markers.

This is invaluable for debugging — comment out a block to see if removing it fixes a bug. Or use it to test one version of code while keeping the old version nearby.

Use // for single lines. Use /* */ to disable an entire block at once. When you use /* */ to comment out a block, watch for any */ sequences already inside that code — they would end your comment early.

Commenting Out — Patterns
// Comment out a single line: // printf("This line is disabled\n"); // Comment out a block with /* */: /* printf("Line A\n"); printf("Line B\n"); printf("Line C\n"); */ // Keep old code nearby while testing new code: // int result = old_method(x); // old approach int result = new_method(x); // new approach
💡
Debugging Pattern
Comment out sections of code one at a time to narrow down where a bug is. If commenting out a block makes the bug disappear, you found your section. This is called binary search debugging.
🌍 Comment-out in real debugging

Every programmer comments out code during debugging. It is one of the fastest ways to isolate a problem without losing your work.

/* Temporarily disabled — causes crash when input is empty
if (process_input(buf)) {
    write_output(buf);
}
*/
// Use safe fallback while investigating:
write_output("[empty]");
